# 宠物记忆产品文档职责说明

版本：v0.4  
首次确认：2026-07-20  
更新：2026-07-26  
状态：M0 开工前与实施期间的文档职责入口

完整目录见 [docs/README.md](../../README.md)。本文件只说明各类文档的职责，避免重复写规则。

## 0. 交付阶段

- `M0`：本地 Mock 骨架，只验证页面、状态、视觉、本地文字数据和受控 AI mock；
- `M1`：CloudBase Private Alpha，承载邀请制真实私密测试；
- `M2`：在 M1 反馈之后再决定的提醒、分享、纪念创作等扩展。

基础文档中的“长期方向”不等于当前交付范围。“MVP”专指 `M1`，“Mock 骨架”专指 `M0`。

## 1. 产品基础

目录：`docs/product/foundation/`

| 文件 | 回答的问题 |
|---|---|
| `2026-07-15-pet-memory-core-design.md` | 为什么做、服务谁、体验原则和长期边界 |
| `2026-07-16-pet-memory-scenario-map.md` | 基础场景及 P0/P1/P2 优先级 |
| `2026-07-16-pet-memory-core-business-rules.md` | 共用状态、内容流转、权限与安全出口 |
| `2026-07-16-pet-memory-user-scenarios.md` | 规则在具体用户旅程中的表现 |

产品基础是长期约束。新增功能不能绕过其中的“真实内容优先、用户控制、默认私密、AI 不越界”原则。

## 2. 正式 MVP 决策

目录：`docs/product/mvp/`

`2026-07-20-formal-mvp-decision.md` 是 `M1` 的范围基线。它只负责确定：M1 用户结果、P0 功能、数据与隐私底线、AI 实施契约、测试成功标准，以及进入技术计划前的待决项。

新需求先判断是否改变该 MVP 边界；如不改变，再回到基础文档核对规则与场景。

## 3. 实施计划

目录：`docs/product/plans/`

技术方案、页面实现与测试计划必须在 MVP 决策确认后编写。计划引用产品基础与 MVP 决策，不在计划内重新定义产品原则。

## 4. 工程决策

目录：`docs/product/technical/`

工程决策确定客户端、后端、数据、环境隔离、安全边界与开发工作流。页面实现或云函数开发前，必须先遵守相应工程决策；不能以工具便利为由突破产品隐私或 AI 原则。

## 5. M0 页面、工程与设计决策

目录：`docs/product/specs/`

已确认的页面、按钮、弹窗、视觉、状态、Repository、路由、测试和 mock 行为记录在此目录。它们是 M0 实施计划的直接输入；未写入该目录或明确列为后续阶段的细节，不得自行实现。

## 6. 历史验证资料

目录：`docs/archive/prototype-validation/` 与 `archive/prototype-validation/`

验证原型的设计、计划、源码、测试和截图均已归档。它们是重要的学习记录，但不再是新增正式功能的默认实现基础；正式产品应按当前 MVP 决策重新建立工程结构。

## 7. 使用顺序

1. 先阅读 [`docs/README.md`](../../README.md)，确认当前阶段、正式入口与最新实施状态；
2. 阅读产品基础，核对体验原则、业务规则与安全边界；
3. 阅读正式 MVP 决策，判断需求是否属于 `M1`，并核对当前工作是在 `M0` 还是 `M1`；
4. 阅读工程决策，确定客户端、数据、环境与工具边界；
5. 阅读当前页面、状态与设计规格；涉及 Task 2 时，以 `2026-07-24-m0-design-system-engineering-spec.md` 为唯一视觉工程真源；
6. 阅读经确认的实施计划，按 Task 顺序执行，不从历史原型补充规则；
7. 实现后，将可复用规则回写到产品基础、MVP、工程决策或页面规格，而不是留在单个页面或临时实现中。
