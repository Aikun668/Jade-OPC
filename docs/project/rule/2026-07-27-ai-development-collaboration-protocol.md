# AI 开发协作与验收协议

日期：2026-07-27  
适用范围：My-OPC 当前 M0 Task 及后续工程开发

## 1. 目的

本协议用于协调项目负责人、Codex 与 DeepSeek Builder 的分工，解决以下问题：

- 正式规格已经清楚，但实现仍出现遗漏、占位和接口漂移；
- 测试、类型检查或构建通过，却没有证明真实要求已经满足；
- Builder 在独立验收前提前宣布 Task 完成并修改总进度；
- 为弥补执行问题不断扩写规格，造成上下文越来越长。

本项目后续不以“继续无限细化规格”为主要解决方式，而采用：

```text
正式规格
→ 小批次执行合同
→ Builder 实现与自证
→ 独立只读复核
→ 关键里程碑验收
→ 更新正式进度
```

## 2. 三方角色

### 2.1 项目负责人（用户）

项目负责人是产品与重要工程决策的最终确认者，负责：

- 确认产品范围、用户流程、重要视觉、接口变更和架构选择；
- 决定是否接受 A/B 方案及其影响；
- 提供必须由人完成的 HBuilderX、微信开发者工具和真机操作；
- 决定是否允许进入下一阶段。

项目负责人不需要亲自判断每个技术实现细节，也不负责替 Builder 编写测试或寻找遗漏。

### 2.2 Codex（规划者与关键验收者）

Codex 负责：

- 维护产品、架构、任务边界和事实真源的一致性；
- 将复杂需求整理为正式决策、规格和实施计划；
- 判断问题属于规格缺失、执行偏差、技术冲突还是验证不足；
- 在高风险里程碑进行独立验收；
- 根据真实证据给出 `通过 / 修复中 / 外部阻塞` 结论。

Codex 不承担每个小步骤的日常盯工，避免把高成本验收资源消耗在低风险细节上。

### 2.3 DeepSeek Builder（实现者）

Builder 负责：

- 完整阅读当前 Task 相关规格、计划和复盘；
- 开工前把规格转换为本轮执行合同；
- 按批准范围实现代码，不自行修改产品或固定接口；
- 先建立会失败的验证，再实现修复；
- 运行测试、类型检查、构建、产物和真实工具链检查；
- 如实报告未验证项、警告、占位内容和外部阻碍。

Builder 可以报告“实现完成”和“自测完成”，但不能在独立验收前自行宣布正式 Task 通过。

### 2.4 DeepSeek Reviewer（独立复核角色）

在额度允许时，使用一个全新的 DeepSeek 会话承担 Reviewer 角色。Reviewer：

- 不继承实现会话的结论；
- 默认只读，不直接修改代码；
- 逐条对照规格、固定接口、禁止项和完成条件；
- 检查测试是否能在错误实现下失败；
- 查找占位资源、TODO、接口漂移、隐藏实现和虚假完成状态；
- 输出问题后，再交回 Builder 修复。

Builder 与 Reviewer 可以使用同一种模型，但必须使用相互独立的上下文。

## 3. 八项执行规则

### 3.1 冻结已经确认的规格

已经确认的产品、架构和设计规格原则上保持稳定。

发现问题时先分类：

| 问题类型 | 处理方式 |
|---|---|
| 正式规格没有定义 | 提出方案，由项目负责人确认后补规格 |
| 规格已经定义但实现遗漏 | 修复实现与测试，不继续扩写规格 |
| 规格与平台能力冲突 | 提供证据和 A/B 方案，确认后调整 |
| 测试通过但真实行为错误 | 修复验证方法，不用增加测试数量掩盖 |
| 只有文档状态过时 | 在验收通过后同步原有状态文档 |

不得把 Builder 的执行偏差自动解释为“规格颗粒度还不够细”。

### 3.2 按可验收批次执行

正式 Task 名称保持不变，但执行时可以拆成若干内部批次。批次边界必须满足：

- 范围可以被一次完整理解；
- 产出可以独立测试；
- 复核者可以单独判定通过或退回；
- 不依赖尚未确认的后续实现。

示例：

```text
Task 3A：领域类型
Task 3B：快照与不变量
Task 3C：Repository 写入
Task 3D：失败与原子性
Task 3E：Task 3 集成验收
```

这里细化的是验收批次，不是继续增加产品规格篇幅。

### 3.3 开工前提交规格追踪表

Builder 在每个批次开工前，先提交以下表格：

| 规格要求 | 实现文件 | 验证方法 | 禁止项或风险 |
|---|---|---|---|
| 要实现的明确行为 | 将创建或修改的文件 | 测试、命令或人工操作 | 不得越过的边界 |

追踪表还必须声明：

- 本批次允许修改的文件；
- 固定接口和不得改名的字段；
- 需要项目负责人确认的歧义；
- 预计运行的测试、类型检查和构建命令；
- 不能自动完成的外部验证。

存在影响产品、架构、数据、隐私或固定接口的歧义时，先停止并请求确认。

### 3.4 分离实现完成与正式完成

统一使用以下状态：

| 状态 | 含义 |
|---|---|
| `implementing` | 正在实现，不能勾选完成 |
| `self-verified` | Builder 已实现并自测，等待独立复核 |
| `needs-fix` | 独立复核发现阻断问题 |
| `externally-blocked` | 代码已满足要求，但真实外部工具或人工操作待完成 |
| `accepted` | 完成条件全部满足，独立验收通过 |

只有 `accepted` 才允许：

- 宣布 Task 正式完成；
- 更新 README 总进度；
- 勾选全部完成步骤；
- 写入“可以进入下一阶段”。

Builder 不得先修改完成状态，再等待验收者证明它是否正确。

### 3.5 实现与复核使用独立上下文

推荐流程：

```text
DeepSeek Builder 会话 A
→ 实现与自测
→ DeepSeek Reviewer 会话 B 只读复核
→ Builder A 修复
→ Reviewer B 复核关闭问题
→ 必要时提交 Codex 里程碑验收
```

Reviewer 必须重点检查：

- 规格写了但代码没有执行；
- 测试只检查文件、字符串或类名存在；
- 占位图、空函数、TODO 和“以后替换”；
- 构建没有包含声称已经验证的代码；
- 新增接口、颜色、依赖或状态没有正式授权；
- 文档完成结论早于验证证据。

### 3.6 使用要求覆盖率，不使用测试数量代替质量

“通过 200 项测试”不能单独证明完成。每个高风险要求必须形成证据链：

```text
规格条目
→ 能暴露错误实现的失败测试
→ 正式实现
→ 测试通过
→ 必要的构建产物或人工操作证据
```

收口报告优先说明：

- 哪些规格已经被验证；
- 测试如何证明真实行为；
- 哪些错误实现会使测试失败；
- 哪些状态只能通过微信开发者工具或真机验证。

不得用重复、静态或无行为意义的测试数量制造完成感。

### 3.7 每个 Task 建立统一验证入口

每个正式 Task 应逐步形成单一验证入口，例如：

```powershell
npm run verify:task3
```

验证入口根据 Task 风险组合执行：

```text
依赖检查
→ 固定接口检查
→ 单元与组件测试
→ 失败和边界测试
→ TypeScript 类型检查
→ 微信生产构建
→ 构建产物检查
→ 禁止项扫描
```

禁止项扫描至少包含：

- `TODO / FIXME / 以后替换 / placeholder`；
- 未批准的接口和依赖；
- 私有魔法颜色、字号和尺寸；
- 空白或伪造的视觉资产；
- 临时测试输入、输出和调试日志；
- 未经验证的“全部完成”“0 warnings”等状态声明。

一项失败时，命令必须返回失败；不得只输出 warning 后继续宣布通过。

### 3.8 Codex 只用于高价值里程碑

为控制额度，默认验收节奏为：

```text
Task 2 地基验收
→ Task 3–4 由 Builder + Reviewer 闭环
→ Task 5–7 主流程验收
→ Task 8–9 由 Builder + Reviewer 闭环
→ Task 10 最终总验收
```

出现以下情况时可以提前请求 Codex：

- 固定接口或架构可能需要改变；
- Repository、照片生命周期、隐私或删除范围存在风险；
- 同一问题经过三轮修复仍无法关闭；
- Builder 与 Reviewer 对正式规格理解不一致；
- 测试通过但微信运行结果不一致。

普通命名、测试夹具、小型样式修正和已批准范围内的实现细节，不需要逐项消耗 Codex 验收。

## 4. Builder 开工模板

```text
当前批次：

读取的正式文档：
-

本轮规格追踪：
| 规格要求 | 实现文件 | 验证方法 | 禁止项或风险 |
|---|---|---|---|

允许修改：
-

明确不修改：
-

需要确认的歧义：
- 无 / 具体问题

计划验证：
-

外部验证：
- 无 / 需要项目负责人完成的操作
```

项目负责人或规划者确认追踪表没有重大偏差后，Builder 再开始编码。

## 5. Builder 收口模板

```text
当前状态：
- self-verified / needs-fix / externally-blocked

本轮完成：
-

规格覆盖证据：
| 规格要求 | 实现位置 | 测试或操作 | 结果 |
|---|---|---|---|

实际运行：
- 命令：
- 退出码：
- 测试通过/失败数量：
- warning：

构建与产物：
-

用户如何打开和检查：
-

尚未验证或外部阻碍：
- 无 / 具体说明

发现的接口或规格偏差：
- 无 / 具体说明

建议结论：
- 等待独立复核，不自行宣布 accepted
```

## 6. 独立 Reviewer 模板

```text
本轮只读复核，不直接修改代码。

请逐条检查：
1. 规格追踪表是否覆盖正式完成条件；
2. 固定接口是否发生漂移；
3. 是否存在占位、TODO、空资产或隐藏实现；
4. 测试是否验证真实行为，而不是只验证字符串存在；
5. 微信构建是否实际包含声称已验证的代码；
6. 失败、边界、恢复和清理路径是否覆盖；
7. 完成状态和文档是否早于证据；
8. 是否存在未获批准的产品、架构、依赖或视觉变化。

输出：
- 阻断问题；
- 非阻断问题；
- 每项证据；
- 推荐修复；
- accepted / needs-fix / externally-blocked 建议。
```

## 7. 使用原则

本协议约束的是 AI 协作与交付方式，不替代产品规格、技术决策或实施计划。

发生冲突时：

1. 产品行为以正式产品决策和最新规格为准；
2. 工程边界以技术决策和实施计划为准；
3. 本协议负责规定如何实施、验证、复核和宣布完成；
4. 未经独立证据支持，不得以模型自信、测试数量或构建成功代替正式验收。
