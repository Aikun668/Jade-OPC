# Task 1 工程执行复盘

日期：2026-07-26  
适用范围：M0 Task 2–10 及后续工程任务

## 结论

Task 1 的工程结果最终通过，但执行过程经历了多轮补正。问题不在于不会实现，而在于过早宣布完成、局部修改后缺少全局复核，以及没有一次性交付用户真实打开和预览的完整路径。

后续 Builder 必须把“实现、验证、用户接手、文档状态”作为同一个交付闭环。

## 本轮暴露的问题

| 不够优雅的行为 | 后果 | 后续要求 |
|---|---|---|
| 外部预览和文档状态尚未完成时宣布 Task 完成 | 完成状态失真，下一任务无法可靠开始 | 区分“代码完成”“外部验证待完成”“Task 正式完成” |
| 收到一个问题只修一个文件 | 同一事实继续在其他文档中冲突 | 每次修改后检查 README、实施计划、技术决策和专项规格 |
| 只根据当前终端判断工具未安装 | 混淆未安装、未配置、PATH 未刷新和未验证 | 检查实际安装路径、版本、配置和可用性后再下结论 |
| Task 1 提前留下 Task 2 的视觉实现 | 职责越界，样式真源开始分散 | 只实现当前 Task 获批范围，不顺手替后续 Task 做决定 |
| 没有提前说明 HBuilderX 和微信开发者工具如何打开 | 用户在最后一步仍需自行判断目录和模板 | 涉及外部工具时，交付必须包含可照做的打开、运行和预览说明 |
| 依赖后续审计发现收尾问题 | 增加返工轮次，降低交付可信度 | Builder 在汇报完成前必须自行执行一次完整收口检查 |

## 后续强制执行方式

### 开始前

1. 阅读当前 Task 的全部步骤、完成条件和依赖。
2. 列出本轮允许修改的文件、禁止越过的 Task 边界和验证命令。
3. 确认环境事实，不把推测写进正式文档。

### 执行中

1. 只勾选已经执行并有证据的步骤。
2. 不添加后续 Task 才负责的样式、数据、页面或架构。
3. 发现阻碍时明确记录真实原因，不用临时实现掩盖问题。

### 宣布完成前

1. 重新运行本 Task 规定的测试、类型检查和构建。
2. 完成实际工具链验证；无法完成时明确标记外部阻碍。
3. 检查用户能否根据说明打开、运行和预览成果。
4. 同步所有记录当前状态的正式文档和复选框。
5. 未满足完成条件时，只能报告“部分完成”或“等待外部验证”。
